# Data model: first slice

Status: approved 2026-11-14.

This covers only the records the first slice needs: User, Role, Client
Organization, Contact, Opportunity, Project and Activity Event. Proposals,
invoices, time entries, tasks, notes and files come in later releases and are
not modelled here.

## Conventions

- **Ids** are random text ids generated by HQ, never reused.
- **Times** are UTC, stored as ISO 8601 text with exactly three decimal
  places, so they all have the same width. **Dates** with no time (a
  follow-up date) are stored as `YYYY-MM-DD`.
- **Domain code uses `Temporal`**: `Temporal.Instant` for times and
  `Temporal.PlainDate` for dates. It never uses `Date`.
- **The business time zone is `America/New_York`.** "Due today" and business
  days are worked out in that zone, not the server's.
- **Money** is an integer count of minor units (cents) plus a currency code.
  The currency is `USD` for now.
- **Nothing in the slice is deleted.** A client becomes `former`, an
  opportunity becomes `lost`, a project becomes `cancelled`.
- Every table has `created_at` and `updated_at`, except Activity Event, which
  has only `occurred_at`.
- Every change goes through a versioned migration.

## How the records relate

```
Role ──< UserRole >── User
                       │ owns
Client Organization ──< Contact
        │
        └──< Opportunity ──(0 or 1)── Project
                 │                        │
                 └── primary Contact      └── same Client Organization

Activity Event ── points at any one record, written by one User
```

`service` is one of: `consulting`, `landing-page`, `domain-management`,
`website`, `blog`, `social-media`, `application`, `automation`.

### Stage rules

- Stages move forward one step at a time: `new` → `consult-booked` →
  `consulted` → `quoted` → `won`.
- A `landing-page` opportunity may go from `consulted` straight to `won`.
- Any open stage may move to `lost`.
- `won` and `lost` are final. A reopened deal is a new opportunity.
- `won` requires a service, a pricing shape and a value.

## Project

Work Potomac has agreed to do. In v0.2 this is a stub. v0.3 adds phases,
milestones and tasks.

| Field | Type | Rule |
| --- | --- | --- |
| `id` | id | |
| `organization_id` | id | Required. Copied from the opportunity |
| `opportunity_id` | id | Required and unique: one project per opportunity |
| `owner_id` | User id | Required |
| `name` | text | Required |
| `kind` | `fixed` or `ongoing` | `ongoing` when the opportunity's pricing is `monthly` or `yearly`, otherwise `fixed` |
| `status` | `active`, `completed`, `cancelled` | Starts `active` |

### Project rules

- A project is created only by converting a `won` opportunity.
- An opportunity can be converted once.
- A `fixed` project ends as `completed` or `cancelled`.
- An `ongoing` project never becomes `completed`. It stays `active` until it
  is `cancelled`.

## Activity Event

The audit record. One is written for every change to any record above, and
for every sign-in.

| Field | Type | Rule |
| --- | --- | --- |
| `id` | id | |
| `occurred_at` | time | Set by the server |
| `actor_id` | User id | Empty only for actions HQ takes by itself |
| `action` | text | A fixed key, for example `opportunity.stage-changed` |
| `record_type` | text | For example `opportunity` |
| `record_id` | id | The record acted on |
| `context` | JSON | What changed, for example the old and new stage |

- **Events are read in the order they were written**, not by `occurred_at`,
  so a clock that is stepped back cannot reorder the log.
- **Append-only.** There is no code path that updates or deletes an event, and
  database triggers reject any update, delete or replace.
- **`actor_id` is not a foreign key.** The audit table must never be the
  reason a change is refused. Users are disabled, never deleted, so the id
  always resolves.
- **`action` is a dotted lower-case key** and `record_type` is one lower-case
  name.
- **A context key that names a secret is refused**, at any depth: a password,
  token, session, API key or card detail.
- **Sensitive values are referenced, never copied in.** `context` never holds
  a password, a token or a payment detail.
- The record change and its event are written in one transaction. If either
  fails, neither is saved.

### Subtasks and blocking

Added by decision 0007, section 5 (migration 0043).

`task.parent_id` points at the task a subtask belongs to. Subtasks go one
level deep, under project tasks only (to-dos have no project to share), and
are made in their parent's project and phase. A parent shows "3 of 5 done";
finishing it doesn't finish its subtasks.

`task_block` says one task waits on another:

| Field | Type | Rule |
| --- | --- | --- |
| `blocked_id` | Task id | The task that waits |
| `blocker_id` | Task id | What it waits on, in any project or none. Never the same task |
| `created_by` | User id | Who said so |

No circles: a task can't wait on anything that already waits on it, however
far back. Waiting never stops a move; moving a waiting task to "working on"
says what it still waits on. This is separate from the "Blocked" status,
which is still set by hand. Events: `task.added` (with `parentId`),
`task.blocked`, `task.unblocked`.

### Notices and reminders

Added by decision 0007, section 8 (migration 0046), in the `notices` module.

`notice` is something new for one person: `assigned` (a task or to-do given
to them by someone else, when added or reassigned), `mentioned` (an
`@mention` in a comment, new or edited in) or `reminder`. Assignments and
mentions are made from the events the projects and todos modules record, in
the same transaction, by the activity log they're given; no one is told
about their own actions, and a repeat's next task isn't news. A notice has
`read_at`, set when it's opened or all are marked read, and `emailed_at`.

`task_reminder` is a reminder on a task: either at a time (`at`, fired
once), or `days_before` its due date (0 to 30) at a `time_of_day` in the
business time zone, which fires again for a new due date. `for_whom` is `me`
(its setter, and only they see it) or `assignee` (whoever has the task when
it fires, or its setter if no one does; everyone who sees the task sees it,
and anyone with `task.edit` may remove it). With `carry`, finishing a
repeating task copies it to the next one: one before the due date as it is,
one at a time moved as many days as the due date moved (in the business
time zone). Nothing fires for a task that's done. A job fires them every
minute.

`notice_setting` holds whether a person has their notices emailed (off until
they turn it on; turning it on covers what comes from then, not what's
already there). When email is set up, a job emails each of them their new,
unread notices every minute, one email per person, each notice once.

Events: `reminder.added`, `reminder.removed`, `reminder.fired`,
`user.notice-email-on`, `user.notice-email-off`. `task.edited` now also
records `assigneeWas`, and `task.repeated` records `previousDueOn`.

### Repeating tasks

Added by decision 0007, section 7 (migration 0045). Four columns on `task`:

| Field | Type | Rule |
| --- | --- | --- |
| `repeat_every` | 1 to 365 | With the next two: all set, or none |
| `repeat_unit` | `day`, `week`, `month`, `year` | |
| `repeat_from` | `due`, `done` | Counted from the due date, or from the day it was done |
| `previous_id` | Task id | The task whose finishing made this one. At most one task per previous |

Finishing a repeating task, from the board, its page or My work, makes the
next: the same title, details, person, priority, estimate, phase, labels,
client (for a to-do) and subtasks (not done, with their dates moved as far
as their parent's), due on the next date. Counted from the due date, that is
the first one after the day it was done; with no due date, it counts from
the day it was done. Months keep their day where they can. Finishing it again
after reopening makes no second one, and nothing is made for a task on a
project that isn't active. Subtasks don't repeat on their own. To-dos can.
Events: `task.repeat-set`, `task.repeat-stopped`, `task.repeated`.

### Task comments and files

Added by decision 0007, section 6 (migration 0044).

`task_comment`:

| Field | Type | Rule |
| --- | --- | --- |
| `id` | id | |
| `task_id` | Task id | |
| `author_id` | User id | Only they edit or delete it; no role overrides that |
| `body` | text | 1 to 5,000 characters |
| `edited_at` | time | When it was last edited, shown as "(edited …)" |

Deleting a comment removes its row. Every version and the deletion stay in
the task's history as events: `comment.added` (with `body` and the people it
`mentions`), `comment.edited` (with `was`, `body`, and anyone newly
mentioned) and `comment.removed` (with `was`). A mention is `@` and a first
name, a full name with hyphens, or the name part of an email, meaning one
active person; telling them comes with notices (section 8).

Files attached to a task are rows in `file` with `owner_type` `task`, filed
under the project's client or a to-do's own, with the same type checks as a
deliverable. Downloading goes through `/files/:id` and `file.download`.
Events: `task.file-attached`, besides the files module's `file.uploaded`.
A task's file can be removed from that task, which deletes its bytes and its
record (`task.file-removed` and `file.removed`, which keeps the name, size and
hash). Only files whose owner is that task: a deliverable's or a receipt's
file can't be removed this way.

### Quick add

Added by decision 0007, section 4. No table of its own: a line typed at
`/add` (or in the top bar's box, or after pressing N) becomes a row in
`task`, with `created_by` set to whoever added it. `+handle` names an open
project, which makes a project task, or else a client, which makes a to-do
with `organization_id` set. A to-do with no `@person` is the adder's; a
project task with none is no one's, as on the project page. New `*labels`
are made on the way. Events are the usual ones (`task.added` or
`todo.added`, with `quick: true`, then `label.added` and `task.labelled`).

One uploaded file (decision 0002).

| Field | Type | Rule |
| --- | --- | --- |
| `id` | id | Its only address is `/files/<id>` |

## v0.4: proposals and estimates

Decided 2026-11-16 while Mikey was away. Needs his approval.

### Proposal

What Potomac offers to do for an opportunity, and for how much. An
opportunity can have several: a declined one stays, and a new one is started.

| Field | Type | Rule |
| --- | --- | --- |
| `id` | id | |
| `opportunity_id` | id | Required. The opportunity must be open when the proposal is started |
| `title` | text | Required. Starts as the opportunity's title |
| `status` | `draft`, `sent`, `revised`, `accepted`, `declined` | Starts `draft` |
| `pricing` | `free`, `hourly`, `fixed`, `monthly`, `yearly` | The same shapes an opportunity has |
| `scope`, `deliverables`, `assumptions`, `exclusions` | text | The four sections. A line starting with a dash is a list item |
| `lines` | estimate lines | The working copy's estimate |
| `current_version` | integer | The last version sent. 0 before the first |
| `shared_with_client` | yes or no | Whether the client sees sent versions in the portal (v0.6) |

An **estimate line** is an item, a kind (`hours` or `quantity`), a quantity
kept in hundredths, a rate in cents and their total. At most 40 lines.

### Status rules

- `draft` → `sent` by sending. Sending needs at least one line, and a total
  that fits the pricing: zero when free, above zero otherwise.
- Editing a `sent` proposal makes it `revised`. The version that was sent is
  not touched. Sending again makes the next version.
- Only a `sent` proposal can be answered. A `revised` one must be sent first,
  so the answer is always to something the client has seen.
- `accepted` and `declined` are final.
- The opportunity must be `consulted` or `quoted` to send.

### Proposal Version

What was sent: a full copy of the proposal's content with its number, total,
hours, who sent it and when. **Immutable.** Database triggers reject every
update and delete, like the Activity Event table.

### Proposal Decision

| Field | Type | Rule |
| --- | --- | --- |
| `proposal_id` | id | One decision per proposal |
| `version` | integer | The version that was answered |
| `decision` | `accepted` or `declined` | |
| `by_name` | text | Who at the client gave the answer |
| `decided_on` | date | |
| `method` | `in-person`, `phone`, `email`, `signed-paper`, `portal` | `portal` is set by the portal itself (v0.6) |
| `note` | text | Optional |
| `recorded_by` | User id | Empty when the client answered in the portal |

### What sending and accepting do to other records

- **Sending** sets the opportunity's pricing and value from the version, and
  moves a `consulted` opportunity to `quoted`. The value is the total for
  fixed and recurring work, the hourly rate for hourly work, zero when free.
- **Accepting** moves the opportunity to `won` (which makes its client
  `active`), starts the project if it has none, and sets the project's
  baseline. All of it is one transaction.

| Field | Type | Rule |
| --- | --- | --- |
| `id` | id | |
| `proposal_id`, `version` | id, integer | The accepted proposal and version |
| `reference` | text | Words for where the signed copy lives |

### Project Baseline

What was agreed for a project: the accepted version's pricing, total, hours
and lines. One per project. v0.5 measures actual time and cost against it.
A deposit is one third of a fixed total, rounded up to the cent. It is shown
on the proposal and is not stored.

### Templates

One per launch service, in code (`src/proposals/domain/templates.ts`), with
the list prices from `docs/workflow.md`. A template only fills a new draft:
every word and number can be changed before sending.

## v0.5: time, expenses and budgets

Decided 2026-11-16 while Mikey was away. Needs his approval. This is a

### Time Entry

| Field | Type | Rule |
| --- | --- | --- |
| `id` | id | |
| `project_id` | id | Required |
| `task_id` | id | Optional. Must be a task of the same project |
| `user_id` | User id | Who worked. Always the person logging it |

**The timer** (docs/workflow.md, B6):

- Moving a task to `doing` ("working on") starts the mover's timer on it, in
  the same transaction as the move.
- A person has at most one timer running. Starting another stops the first
  and logs its time.
- Moving a task out of `doing` stops every timer running on it.
- Time is rounded up to the minute. A timer left running is capped at 12
  hours when it is stopped.

| `budget_minutes` | integer | Set by hand. Empty means the accepted proposal's hours |
| `rate_minor` | money | What an hour of work is counted as costing. Starts at $75 |
| `payment_status` | `not-invoiced`, `deposit-paid`, `invoiced`, `paid` | Starts `not-invoiced`. Set by hand |
| `invoice_ref` | text | The invoice's number or link |

### Estimate against actual

- **Hours:** the budget's hours against time logged.
- **Cost:** the budget amount against time at the project's rate, plus
  expenses.
- **Margin:** the budget amount less that cost. Labelled an operational
  estimate everywhere it is shown.
- **By phase:** a phase's estimate is its tasks' estimates added up. Time
  counts for the phase of the task it was logged on.
- **The period:** a one-time job is measured over all time. A monthly plan is
  measured over the current month and a yearly one over the current year,
  because their price is for one period.
- A project with no budget is never "over".

### Invoice

Invoicing is built into HQ (docs/tool-boundaries.md).

| Field | Type | Rule |
| --- | --- | --- |
| `id` | id | |
| `project_id` | id | Required |
| `number` | integer | 1, 2, 3 in the order invoices are made, with no gaps. Shown as `INV-0001` |
| `kind` | `deposit`, `balance`, `full`, `other` | What it is for |
| `status` | `draft`, `sent`, `paid`, `void` | Starts `draft` |
| `lines` | description and amount, each | At least one, at most 30 |
| `total_minor`, `currency` | money | The lines added up. Above zero |
| `issued_on` | date | Set to today when sent |
| `due_on` | date | Optional |
| `note` | text | Optional. Printed on the invoice |

- A draft can gain lines. Sending locks it: it is what the client was asked
  to pay.
- A mistake is voided, never deleted. An invoice with a payment against it,
  or a paid one, cannot be voided.
- A sent or paid invoice has a PDF. A draft does not.

### Payment

Money received against a sent invoice. Written once.

| Field | Type | Rule |
| --- | --- | --- |
| `id` | id | |
| `invoice_id` | id | The invoice must be `sent` |
| `amount_minor`, `currency` | money | Above zero. Payments never add up to more than the invoice |
| `method` | `cash`, `check`, `card`, `transfer`, `other` | `card` means through a gateway |
| `received_on` | date | Not in the future |
| `reference` | text | A check number or a gateway's reference. **Never a card number:** text that looks like one is refused |

When payments reach an invoice's total it becomes `paid`. The project's
payment status then follows by itself: sending an invoice makes it
`invoiced`, a paid deposit makes it `deposit-paid`, and any other invoice
paid with none left waiting makes it `paid`. It can still be set by hand,
for a job invoiced on paper.

### Exports and the Google Sheet

Five tables: every time entry, every expense, budget against actual by
project, every invoice, and every payment. Each downloads as CSV, and each
export is an activity event.

The Google Sheet is the book of record for taxes (docs/tool-boundaries.md,
rule 2). When one is set up, HQ copies the five tables to it each night,
into tabs of its own named "HQ Time", "HQ Expenses", "HQ Projects", "HQ
Invoices" and "HQ Payments". It replaces only those tabs, touches nothing
else in the sheet, and never reads the sheet back. Text that a spreadsheet
would run as a formula is defused in the CSV, and written as plain text to
the sheet.

## v0.6: the client portal

Decided 2026-11-16 while Mikey was away. Needs his approval.

### Client User

Someone at a client who may sign in to the portal. Separate from a User: a
client user has no role and no permission, and belongs to exactly one client
organization.

| Field | Type | Rule |
| --- | --- | --- |
| `id` | id | |
| `organization_id` | id | Never changes |
| `name` | text | Required |
| `email` | text | Lower case, unique across all client users |
| `status` | `invited`, `active`, `disabled` | `invited` until they use their link |
| `portal_account` | text | The account they sign in with. Empty until they accept |
| `invited_by` | id | The HQ user who invited them |

- A client user gets in by a link that works once and lasts a week. With
  email set up the link is emailed to them. Without it, it is shown once to
  the person who made it, to send by hand. The link is never stored, and
  never written to the activity log.
- Using the link sets their password, makes them `active` and signs them in.
- A new link is how a forgotten password is fixed.
- Turning access off makes them `disabled`, ends their sessions at once, and
  refuses their password and any link. Turning it back on makes them
  `active` if they had set a password, and `invited` if not.
- Passwords and sessions are kept by a second instance of the kit's `staff`
  module, in `kit_document` collections that start `portal:`, with a cookie
  of its own (`hq_portal`). An HQ session and a portal session cannot stand
  in for each other.

### Project Update

What Potomac tells a client about a project, and what the client writes
back. One list, oldest first. Not the same as a Note: notes are internal and
never reach the portal.

| Field | Type | Rule |
| --- | --- | --- |
| `id` | id | |
| `project_id` | id | |
| `user_id` | id, optional | Set when Potomac wrote it |
| `client_user_id` | id, optional | Set when the client wrote it. Exactly one of the two is set |
| `body` | text | Required, 5,000 characters at most |

Written once. Never edited or removed.

### Call Request

A client asking for a call, and Potomac's answer. This is the booking tool of
`docs/tool-boundaries.md` at its smallest: there is no calendar.

| Field | Type | Rule |
| --- | --- | --- |
| `id` | id | |
| `organization_id`, `client_user_id` | id | Taken from the client's session |
| `wanted` | text | When they would like to talk, in their words |
| `note` | text | What about |
| `status` | `requested`, `confirmed`, `declined` | Answered once |
| `confirmed_for` | text | Required when confirmed |
| `reply` | text | Potomac's words back |
| `answered_by` | id | The HQ user who answered |

### Files a client sends

A client can send a file on one of their own active projects. It is a File
like any other (v0.3), filed under owner type `client-upload` with the
project as its owner, belonging to the client's organization and visible to
it. `uploaded_by_client` names the client user, and `uploaded_by` is empty.
A project takes at most 20 a day this way. Receiving one writes
`file.received-from-client`, which shows in the project's history.

A Call Request also carries `phone`: the number to call back on, as the
client typed it. Optional. Digits with the usual punctuation, at least
seven of them.

### Whose step it is, and notices

- A Milestone carries `for_client`: true when it is the client's to do.
  Potomac sets it when adding the milestone, or later. The portal lists a
  client's open ones as waiting on them.
- A Client User carries `notices`: whether they are emailed when something
  is waiting. On to start. Only they change it.
- `notice_cursor` is one row: how far through the activity log the notice
  sender has read. It is not a business record.

### What a client's actions do to other records

- **Approving a deliverable, or asking for changes,** is the same change as
  when Potomac records it (v0.3), with `decided_by_client` set to the client
  user. Asking for changes needs a reason.
- **Accepting a proposal** is the same change as when Potomac records it
  (v0.4): the opportunity is won, its project starts, and the baseline is
  set, as one change. The decision's `method` is `portal`, `by_name` is the
  name they typed, and `recorded_by` is empty.
- Every one of these writes an activity event with no HQ actor and the
  client user's id in its context.

### Article

One entry in the knowledge base. A decision is an article with the day it

| Field | Type | Rule |
| --- | --- | --- |
| `id` | id | |

### Reports

Reports are read from the records above and store nothing.

### Two-factor sign-in

Decided 2026-11-22 while Mikey was away. Needs his approval.

| Table | Holds |
| --- | --- |
| `user_two_factor` | One per user who has started turning it on: the shared secret (base32), when it was confirmed, and the last 30-second step a code was accepted for |
| `two_factor_recovery` | Ten per user: a SHA-256 hash of each recovery code, and when it was used |
| `two_factor_session` | Sessions that have passed the second step, keyed by the same hash of the session id the kit keys sessions by |

- Codes are six digits, 30 seconds each (RFC 6238, SHA-1), the kind every
  authenticator app makes. A code for the step before or after is accepted,
  for a phone whose clock is off. None is accepted twice.
- It only counts once confirmed with a code. Turning it off, or an admin's
  reset, removes all three.
- Events: `user.two-factor-on`, `user.two-factor-off`, `user.two-factor-new-codes`,
  `user.two-factor-reset`, `user.two-factor-passed` and
  `user.two-factor-recovery-used`. None carries a code or the secret.

## Storage for the kit

The kit's `staff` module keeps its accounts and sessions through a store
adapter. That adapter uses one table, `kit_document` (`collection`, `key`,
`fields`), in the same database. No HQ code reads it directly. The portal's
accounts are in the same table, in collections that start `portal:`.
